# Life Board 桌面端落地 · 最终方案建议

> 对象：Life Board（人生看板）· 结论日期：2026-08-15
> 前提：本仓库当前为「五板块广度 MVP」Web 应用（Vite 5 + React 18 + TS strict + Zustand persist(localStorage)），目标是**在电脑端日常使用**。

## 0. 一句话结论

**先留在浏览器里用起来，本周就套 Tauri 2 壳；数据层从 localStorage 迁到 IndexedDB 并加迁移与自动备份；云同步与 monorepo 一律推迟到真正出现第二台设备的需求。** UI 语言（暖纸白 + 深林绿 + 板块身份色）已经成熟，不重做，只补桌面专属交互。

## 1. 形态决策：电脑端到底做成什么

| 方案 | 结论 | 理由 |
|---|---|---|
| 纯浏览器 + PWA | 可用，但不是终点 | 浏览器里标签页多、容易被误关/清缓存、没有托盘与全局快捷键，长期使用体验打折 |
| Electron | ❌ 排除 | 体积/内存劣势，且与架构文档（Tauri 2 已定）冲突 |
| **Tauri 2 壳（沿用现有 Web 代码）** | ✅ **选它** | 与 docs/技术架构方案.md 一致；现有代码已 Tauri-ready（纯静态站点 + 零 Node 运行时依赖）；产物约 10MB；不需要写 Rust 就能先跑起来 |

**关键认知**：套壳不是「重写」，是把现有 npm run build 的 dist/ 装进一个原生窗口。数据、UI、逻辑一行不改，先拿到这些原生能力：

- 窗口状态记忆（大小/位置/最大化，关掉重开回到原样）
- 系统托盘常驻 + 全局快捷键（如 ⌘⇧K 任意时刻唤起「记录」浮层）
- 开机自启（可选开关）、Dock 图标、原生通知（如每周复盘提醒）
- 文件系统写入（自动备份 JSON 到 ~/Documents/Life Board/）
- 摆脱浏览器对 localStorage 的配额与「清除浏览数据」风险

**实施（约 1–2 天）**：Rust 工具链装一次（cargo + tauri-cli，或 npm i -D @tauri-apps/cli），npx tauri init 指向现有项目，配 3 个插件即可：window-state、global-shortcut、autostart；备份写文件用 tauri-plugin-fs + capability 配置。此阶段零业务代码改动。

## 2. UI 层建议：不换气质，补桌面体验

现有设计语言（4 级暖灰墨阶、卡片靠边框、大数字负字距、色即图例、深色跟随系统）对标 Things/Linear，**已经是这个项目最大的资产，保留**。要补的是「桌面大屏 + 键盘流 + 长期数据」三件事：

### 2.1 桌面布局
- 侧栏折叠已有（⌘B）；二级子页（约 25 个，当前点开是「即将上线」）落地时采用**两栏：左列表 + 右详情**，而不是单列长卡片堆叠——这是 Things 3 式桌面管理页的形态，信息密度更高。
- 窗口宽度自适应：内容区设 max-width + 居中（大屏不拉满），已在原型精神内，落地子页时统一成布局组件。

### 2.2 键盘流补全（对齐「桌面工具」定位）
| 快捷键 | 功能 | 状态 |
|---|---|---|
| ⌘1 – ⌘8 | 八个 tab 直达 | 目前只有 ⌘1，补 2–8 |
| ⌘, | 设置 | 新增 |
| ⌘⇧K（全局） | 任意应用内唤起记录浮层 | Tauri 全局快捷键 |
| ⌘F | 板块内过滤 | 子页落地时加 |
| Esc 逐层关闭 | 浮层 → 子页 → tab | 已有浮层部分 |

### 2.3 数据可信感（桌面工具与玩具的分水岭）
- 设置页展示：记录总数、各板块数据量、最近一次自动备份时间、存储占用。
- 空状态升级：无数据时给「3 分钟上手」三步引导（录一条 → 建一个目标 → 看一眼总览），而不是干巴巴的「暂无数据」。
- 清空/导入等危险操作已有确认弹层，保留。

### 2.4 导出与复用（对齐 PRD §1.2「一条信息只录一次」）
- 增加**周报/月度复盘导出 Markdown**（工作板块成果 + 财务小结 + 健康趋势自动归集成文），这是 PRD 反复强调的复用场景，也是桌面端最能体现价值的按钮。
- JSON 备份已具备；补一键「导出全部为 Markdown/CSV」即可，无需表格组件库。

### 2.5 明确不做
- 不做主题换肤（身份色已承担区分职能）；不引入组件库/图表库（手写 SVG 图表已够，且是零依赖卖点）；不做多窗口/多实例（单窗口 + 托盘足够）。

## 3. 代码层建议（按优先级）

### P0 · 数据安全（现在就要做）

1. **给 persist 加 migrate**（src/store.ts）：当前 version: 1 且无 migrate 回调。数据是产品本体（「一条信息只录一次」意味着越用越珍贵），模型一改，旧 localStorage 数据会被静默读错。从今天起每次改 types.ts 就 bump version + 写 migrate。
2. **自动备份双保险**：Tauri 壳就绪后，每次启动/每日首次写入时把完整数据 JSON 写到 ~/Documents/Life Board/backups/（带日期），设置页可手动触发。浏览器阶段则保留现有导出 JSON。

### P0 · 存储升级：localStorage → IndexedDB

现状风险（已核实代码）：
- persist + createJSONStorage(localStorage) **每次任何写入都把全量 AppData JSON.stringify 一遍**（addEntry 等每个 action 都触发），数据到几千条后每次输入都有肉眼可见卡顿；
- 浏览器 localStorage 配额约 5MB；按每天 5–10 条记录估算，**2–3 年就会触顶**，而人生看板恰恰是设计给「长期积累」的。

方案：**Dexie**（或更薄的 idb）按集合存 entries / txs / readings 等，查询走索引（按 date、areaKey、kind 过滤）。store 接口形状保持现状（README 已注明「为换 IndexedDB/SQLite 预留」），替换点集中在 src/store.ts 与新增一个 src/db.ts。迁移脚本：读旧 localStorage key life-board:data 一次性倒入。

### P1 · 工程化补课

- **vitest 给 src/lib.ts 写单测**：日期计算（周一为周起点、月末、相对日期）、monthSummary（转账不计、退款冲减口径）、goalPace 都是纯函数且极易错，这是性价比最高的一笔测试投入；现有 scripts/verify-roundtrip.ts 只是数据往返脚本，不是测试。
- **ESLint + Prettier**：当前缺失；TS strict 已开，很好，补上 lint 让格式纪律落地（与视觉报告强调的「token 纪律」同构）。
- **CI**：一个 GitHub Actions（tsc --noEmit + vitest + build），Tauri 加打包 job 可后置。

### P1 · 数据访问抽一层 repository

现在 dataStore 直接暴露所有集合；子页（25 个）落地前，把「读」收敛为查询函数（lib.ts 已有雏形），「写」收敛为 store action。这一层在换 SQLite（架构文档远期）时只需替换实现，UI 不动。**注意不要为此引入 React Query**——单机本地数据用不上缓存层，徒增概念。

### P2 · 首屏性能

8 个板块现在全部常驻渲染（hidden keep-alive）。子页批量落地后改 React.lazy 按板块拆包，首屏只加载 Overview + Calendar。依赖仍保持极简，不引图表库。

### 明确不要做的（重要）

- ❌ **现在不上 monorepo / Turborepo / shared 包**：架构文档的「一套技术栈打三端」是远期方向，但 monorepo 拆分在没有移动端代码时是纯成本。
- ❌ **现在不接 Supabase/云同步**：产品定位是「纯本地、无账号」（视觉报告 Part A 明确定位）；同步只在真正出现「第二台设备」需求时再上，且届时做成**可选**能力，不改变本地优先本质。架构文档路径保留，作为路线图而非近期任务。

### 清理（半天）

- **docs 与代码对齐**（已核实漂移）：
  - docs/PRD-产品需求文档.md 引用的 LIFE_BOARD_IMPLEMENTATION_MATRIX.md 不存在；
  - docs/视觉效果文档报告.md 大量引用 boards.css、refined.css、OverviewRefined.tsx、public/fonts/ 自托管字体，而这些文件在当前仓库都不存在（当前是合并后的 src/styles.css 663 行 + 系统字体栈），报告声明的技术栈是 Dexie/IndexedDB，实际是 localStorage——报告描述的是更早的一次迭代；
  - 建议：要么补回矩阵文件，要么在报告头部加「已归档，仅供参考」标注，避免后续按错误文档开发。
- 根目录 mckinsey_pptx.py / demo_mckinsey.pptx 与项目无关，移入 scripts/ 或独立目录，保持仓库单一主题。

## 4. 实现效果：最终体验验收清单

「最终效果」应该能被以下清单量化验收：

- [ ] 冷启动 < 1s（本机资源，无网络依赖），启动即达上次的 tab 与窗口状态
- [ ] 全键盘可达：任何界面操作（除输入）都能不碰鼠标完成
- [ ] 任意时刻 ⌘⇧K 弹出记录浮层，录入后回车即存，2 秒内完成「记录」动作
- [ ] 数据零丢失：模型升级走迁移；每天一份自动备份文件；设置页可见数据量与备份时间
- [ ] 数据量增长无感知：5000 条记录时输入、搜索、切 tab 依然流畅（IndexedDB + 索引）
- [ ] 周报一键导出 Markdown，可直接粘贴进工作文档
- [ ] 托盘常驻 + 可选开机自启，App 像「系统的一部分」而不是「浏览器里的一个标签」
- [ ] 深色模式跟随系统；空状态、危险操作确认、导出导入均有完整兜底

## 5. 分阶段路线图（每步可独立交付）

| 阶段 | 内容 | 工期 | 交付物 |
|---|---|---|---|
| **M1 桌面壳** | Tauri 2 初始化 + window-state/global-shortcut/autostart 插件 + 托盘菜单 | 1–2 天 | 可双击打开的原生 Mac App（现有全部功能） |
| **M2 数据加固** | Dexie 迁移 + persist migrate 机制 + 自动备份 + vitest 覆盖 lib.ts 日期/财务逻辑 | 3–5 天 | 数据安全基线：迁移、备份、测试三件套 |
| **M3 体验补完** | ⌘1–8 / ⌘,、设置页数据面板、空状态引导、周报导出 Markdown、docs 漂移清理 | 1–2 周 | 达到第 4 节验收清单的桌面工具 |
| **M4（按需）** | 二级子页批量落地（React.lazy 拆包 + 两栏布局）→ 再之后才考虑移动端/Supabase（照架构文档） | 1–2 月 | 25 个子页 → 完整 PRD |

**顺序原则**：先保证「数据永远不丢」（M2），再做「更好用」（M3），再谈「更多功能」（M4）。M1 可以最先做是因为它零风险且立刻改变日常使用体验。
